# Технический code review (frontend)

Дата: 2026‑03‑25  
Репозиторий: внешний сайт компании (SPA)

## Контекст и ограничения

- Цель: оценить качество и архитектуру текущей реализации, **без изменения кода** (в рамках review).
- Примечание: в ходе предыдущих шагов обсуждалась интеграция с backend API; ниже review описывает текущее состояние архитектуры и типовые проблемы/риски.

## 1) Общее качество кода

### Структура проекта

**Плюсы**
- Понятная базовая структура для небольшого SPA:
  - `src/pages/*` — страницы
  - `src/components/*` — секции/компоненты
  - `src/data/translations.ts` — тексты/контент
- Настройки сборки/стилей стандартные для `Vite + React + TS + Tailwind`.

**Минусы / риски**
- Отсутствует слой “доменных данных” (`api/ services/ hooks/ store`), в результате:
  - данные каталога/услуг смешаны с UI‑переводами в `translations.ts`
  - сложно масштабировать каталог, добавлять фильтры/поиск, подключать API
- Есть признаки “лишнего/мёртвого” кода:
  - `src/components/Products.tsx` выглядит как альтернативный каталог, но в роутинге не используется.
- Папка `dist/` присутствует в репозитории — потенциально риск “шума” в git (артефакты сборки).

### Читаемость и логика компонентов

**Плюсы**
- Компоненты в целом прямолинейные, читаемые, без чрезмерной абстракции.
- Tailwind‑классы используются последовательно.

**Минусы / антипаттерны**
- Дублирование логики открытия `ContactForm` в нескольких местах (см. ниже).
- Логика выбора ассетов (иконки/картинки) “зашита” строковыми шаблонами (`service.id → filename`) — хрупко.
- Использование `href="#"` как заглушки — UX‑антипаттерн (скролл вверх, “ломает” историю/якоря).

### Повторяемость кода

- Скролл‑логика “scroll to top” и `window.addEventListener('scroll'...)` повторяется в `ProductsPage` и `Services`.
- Модалки контактной формы рендерятся в нескольких местах.
- Похожие секции (заголовок + разделитель + описание) повторяются без общего `SectionHeader`/`Container`.

### Сложные/запутанные места

- `src/data/translations.ts` — большой монолит: одновременно i18n, каталог продуктов, услуги, тексты страниц.
- Разная структура “товаров” внутри одной модели:
  - большинство категорий — карточки `{name, description, pdfFile}`
  - `basicChemicals` — `{name, description, items[]}` (особая отрисовка)
  Это усложняет типизацию и будущую нормализацию данных.

## 2) Архитектура

### Разделение страниц / компонентов / shared

**Сейчас**
- Layout фактически в `src/App.tsx` (Header → Routes → Footer + модалка).
- Страницы:
  - `/` → `HomePage` (секции)
  - `/products` → `ProductsPage`
  - `/services` → `ServicesPage` → `Services`
  - `/rd` → `RDPage` → `Research`
  - `/contact` → `ContactPage` → `Contact`

**Оценка**
- Для маленького сайта — ок.
- Для роста (каталог, CMS, API, роли, личный кабинет) — потребуется выделение:
  - `src/api/*` (запросы)
  - `src/hooks/*` (хуки данных)
  - `src/types/*` (доменные типы)
  - `src/utils/*` (утилиты, форматтеры)

### Слой данных

**Отсутствует.**  
Нет сервисов/хуков/кеша. Данные берутся из `translations.ts`. Это главный архитектурный “узел”.

### Роуты

**Плюсы**
- Роуты понятные и минимальные.

**Минусы / масштабируемость**
- Нет детальных страниц товаров/услуг (всё на одной странице с секциями).
- Нет обработки 404/NotFound.
- В футере есть ссылки `/privacy`, `/terms`, но роутов под них нет (возможны “битые” ссылки).

### “Мешанина” логики и UI

**Сейчас**
- В крупных компонентах (`ProductsPage`, `Services`) смешаны:
  - UI (верстка)
  - UI‑логика (скролл, sticky навигация)
  - работа с данными (чтение из translations / будущие запросы)

Для текущего размера — допустимо, но при интеграции API лучше выносить data‑логику.

## 3) Работа с данными

### Откуда сейчас берутся товары и услуги

- Товары: `src/pages/ProductsPage.tsx` → `src/hooks/useProductsCatalog.ts` → публичный API `GET /api/catalog?lang=...`.
  - секции/якоря формируются по stableKey `category_en`
  - label/описания берутся по активному языку из `category_ru`/`category_kz` (fallback на `en`)
  - PDF: `pdf_url` из API (может быть `null`); при `null` используется fallback из `src/data/fallback/products.ts`.
- Услуги: `src/components/Services.tsx` → `src/hooks/useServicesCatalog.ts` → публичный API `GET /api/catalog?lang=...`.
  - фильтр: `type === "service"`
  - группировка: `category_key`
  - описание группы: `category_description` (показывается один раз; при `null` не отображается)
  - карточки услуг: `name` + `description`
- Изображения категорий/услуг и PDF/файлы формируются через `assetUrl()` с учетом `base` (`/home/` в production).

### Насколько удобно перевести каталог на backend API

**Умеренно удобно**: UI уже есть, но потребуется рефакторинг источника данных.

**Главные места, которые придётся переписывать**
- `src/pages/ProductsPage.tsx` — загрузка/группировка, состояния загрузки/ошибок, модель карточек.
- `src/components/Services.tsx` — аналогично по услугам.
- `src/data/translations.ts` — разделить на:
  - UI‑переводы
  - контент каталога (уйти в API)

### Узкие места

- Хрупкие string‑пути к ассетам.
- PDF/файлы с пробелами/скобками в имени: нужен `encodeURIComponent` либо URL от backend.
- `basicChemicals` отдельной структурой — при API важно либо:
  - унифицировать модель, либо
  - иметь явный тип/флаг “isList” и т.д.

## 4) Состояние проекта (production readiness)

### Сборка

- `npm run build` проходит (bundle ~250–260KB JS gzip ~80KB) — ок для лендинга/каталога.

### Линтер

ESLint не проходит “в зелёный” (ошибки уровня `no-unused-vars`, и ранее был `no-explicit-any`):
- неиспользуемые пропсы (`onContactClick`)
- неиспользуемые импорты (`Phone`)
- предупреждение по `ref` cleanup в `Hero`

**Вывод:** для production желательно привести линт к нулю ошибок, иначе качество будет “плыть”.

### Потенциальные баги

- `href="#"` может вызывать неожиданный скролл/перезагрузку якоря.
- Несоответствие якорей услуг в футере и реальных `service.id` возможно (в текущих данных есть риск рассинхронизации).
- “Зависимость” от `base: /home/` и абсолютных путей `/home/*`: при другом деплое сайт может ломаться без корректировки `base/basename`.

### Производительность

- `scroll` listeners без throttling/debounce — не критично для маленького сайта, но можно улучшить.
- Видео в hero/о нас грузится сразу — может быть тяжело на мобильных.
- Нет lazy‑loading для больших медиа.

### Лишние ререндеры

- В целом не критично, но:
  - крупные деревья отрисовываются целиком
  - отсутствие мемоизации и разделения на “чистые” компоненты

### Типизация (TS)

- Есть места со слабой типизацией (`any`) и неоднородной структурой данных.
- Лучше определить доменные типы для:
  - Product
  - Service
  - Category
  - i18n strings

## 5) UX / Frontend best practices

### `key` в списках

Проблема: во многих `.map` используется `key={index}`.  
Рекомендация: использовать стабильный идентификатор:
- сертификаты: `cert.title`
- продукты: `product.name` или `id` (если появится из API)
- услуги: `service.id`

### Lazy loading / code splitting

- Код‑сплиттинга нет (`React.lazy` для страниц). Для лендинга это необязательно, но для каталога/роста полезно.
- Медиа (видео/крупные картинки) можно грузить лениво.

### Обработка ошибок / loading состояния

Сейчас данных с сервера нет, поэтому ошибок/загрузок нет.  
При интеграции API обязательно:
- `loading` состояния на страницах каталога
- “мягкие” ошибки (fallback на статический контент / сообщение)

### SEO

- `index.html` минимальный: нет description/OG.
- SPA без SSR → SEO по каталогу обычно хуже.
Если SEO важно: добавить хотя бы мета‑теги, а дальше рассмотреть prerender/SSR.

## 6) Dev experience

### Поддерживаемость

- Хорошая “визуальная” структура, но нет модульности данных.
- Большой `translations.ts` делает изменения рискованными (легко сломать структуру).
- Линт не зелёный — снижает доверие к качеству.

### Онбординг нового разработчика

- Порог входа средний:
  - понять UI легко
  - понять, почему каталог внутри translations и почему есть `Products.tsx`, сложнее

### Что улучшать в первую очередь

1) Привести ESLint к нулю ошибок.  
2) Разделить data‑слой (API/хуки/типы).  
3) Упорядочить работу с модалками (единое место управления).

## 7) Конкретные предложения по улучшению

### Quick wins (быстрые улучшения)

- Убрать `ESLint` ошибки:
  - удалить/использовать `onContactClick` в `Header` и `Contact`
  - удалить `Phone` import
  - исправить warning `Hero` по `ref` cleanup
- Заменить `key={index}` на стабильные ключи.
- Убрать `href="#"` там, где это заглушки.
- Вынести повторяемые блоки UI (SectionHeader) для единообразия.
- Добавить `NotFound` route и обработку `/privacy`, `/terms` (или убрать ссылки).

### Архитектурные улучшения (среднесрочные)

- Ввести структуру:
  - `src/api/catalog.ts` — функции запросов
  - `src/hooks/useCatalog.ts` — получение + кеширование
  - `src/types/catalog.ts` — доменные типы
  - `src/utils/i18n.ts` — локализация/фолбэки
- Добавить состояния `loading/error` для каталога/услуг.
- Унифицировать модель продуктов:
  - либо сделать “basicChemicals” тем же типом (например `description` + `bullets[]`),
  - либо чётко типизировать “варианты карточек”.

### Что стоит переписать

- `translations.ts`:
  - оставить UI‑переводы
  - убрать из него “каталог” и “услуги” (после интеграции с API)
- Управление `ContactForm`:
  - сделать единый менеджер модалок (Context/микро‑store), чтобы не было 4–5 копий логики.

### Что можно оставить как есть

- Визуальный дизайн/верстку секций (Tailwind‑разметка) — хорошая база.
- Роутинг `react-router-dom` — подходит для SPA.
- Основной layout `App.tsx` — ок, если аккуратно добавить обработку 404/страниц политики.

## Итоговая оценка (1–10) и резюме

**Оценка: 5/10.**

- **Насколько хороший код:** UI аккуратный и читаемый, но есть архитектурный долг (данные в `translations.ts`, отсутствие data‑слоя), дублирование логики модалок и не “зелёный” линт.
- **Насколько готов к росту:** средне‑низко. При росте каталога/локалей/интеграций нужно будет вводить слой данных, типизацию и структуру модулей.
- **Насколько легко подключить backend API CRM:** подключаемо, но потребует рефакторинга ключевых точек (`ProductsPage`, `Services`, `translations.ts`) и добавления `loading/error` и нормализации моделей.
